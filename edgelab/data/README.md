# edgelab.data

**Rôle.** Ingestion (London Strategic Edge, Dukascopy, CSV/Parquet génériques, futures continus), contrôle d'intégrité obligatoire, store des données de marché, sélection par split et lockbox du holdout (I3).

**Décision de design (lockbox).** `HoldoutLockbox.access()` est le seul point d'entrée vers le holdout : il refuse toute raison vide ou composée uniquement d'espaces, journalise chaque accès (stratégie, raison, horodatage) dans une table SQLite append-only — même garde-fou par triggers que le registre d'essais — et renvoie le compteur permanent qui en résulte. `is_flagged()` expose le seuil de trois accès mentionné par I3 pour que l'UI puisse afficher le drapeau rouge sans recalculer la règle elle-même.

**Décision de design (intégrité).** `run_integrity_checks` distingue deux sévérités : `CRITICAL` (`session_gaps`, `duplicate_bars`) déclenche la quarantaine, `WARNING` (`aberrant_ticks`, `zero_volume`, `dst_transitions`, `holiday_anomalies`) figure dans le rapport sans bloquer. Ce n'est pas ce que la spec énumère à plat, mais traiter chaque bascule DST semestrielle comme une quarantaine rendrait l'outil inutile sur toute série de plus de six mois. Le seuil de détection des ticks aberrants est calculé sur un écart-type glissant qui *exclut* le point testé (`shift(1)` avant `rolling_std`) : sinon un pic isolé gonfle son propre écart-type de référence et échappe à la détection.

**Décision de design (futures continus).** `splice_continuous_future` n'a pas de valeur par défaut pour `roll_method` : `RATIO`, `DIFFERENCE` et `NONE` doivent être choisis explicitement à chaque appel. `RATIO`/`DIFFERENCE` back-ajustent l'historique de façon cumulative à chaque roll (méthode Panama) — un contrat plus ancien porte l'ajustement de *tous* les rolls entre lui et le contrat le plus récent, qui sert d'ancre non ajustée.

**Décision de design (Dukascopy).** `parse_bi5` est une fonction pure (bytes -> `DataFrame`), testée sur des flux `.bi5` synthétiques sans jamais toucher au réseau. Le seul point de contact réseau (`fetcher: Fetcher`) est injecté en paramètre, à la frontière du module — le cœur du parsing reste testable en isolation.

**Décision de design (London Strategic Edge).** `lse.py` ne réimplémente pas le SDK officiel `lse-data` : il en isole le contrat derrière le protocole `LseClient`, seul point de contact réseau et seul point injecté dans les tests — même frontière que `Fetcher` pour Dukascopy. Deux chemins d'ingestion, jamais confondus : `ingest_lse_candles` pagine l'API JSON (le vault plafonne à **5 000 lignes par appel** ; sans pagination, demander deux ans de M1 renvoie silencieusement une série tronquée qui passerait pour complète), `ingest_lse_export` déclenche un job d'export Parquet côté serveur pour le volume. La `frequency` du contrôle d'intégrité vient du `timeframe` demandé, jamais des données reçues : la déduire des barres ferait passer les trous d'un dataset pour son pas nominal, et le dataset se validerait lui-même. `normalise_candles` accepte plusieurs alias de colonnes (`ts`/`timestamp`, `o`/`open`, …) et plusieurs encodages d'horodatage, parce que le contrat exact du vault **n'a pas été vérifié contre un serveur réel** — voir « Limite connue » ci-dessous.

**Décision de design (clé API).** `open_client` ne lit plus l'environnement directement : la clé est résolue par `edgelab.settings` (variable d'environnement d'abord, puis fichier local en 0600), et le client réel est enveloppé dans un traducteur d'erreurs. Sans cette enveloppe, une clé expirée ou un quota dépassé remontait en `lse.LSEError` brut jusqu'au CLI — trouvé en exécution réelle, le vault répondant 401 sur une clé bidon. Toute erreur du fournisseur est désormais une `LseDataError`, que chaque appelant sait présenter.

**Décision de design (sélection, `selection.py`).** Le partitionnement `research`/`validation`/`holdout` existait dans le manifeste depuis la Phase 1 mais n'était sur le chemin de personne : `DatasetStore.load_bars` renvoyait le dataset entier, holdout compris, et `BacktestEngine` acceptait n'importe quel DataFrame. I3 et le refus de la quarantaine tenaient donc par discipline. `DatasetSelection` est désormais le seul type que le moteur accepte, et il ne peut pas exister sans que trois choses soient vraies : le manifeste a passé `ensure_backtest_ready`, les barres tombent dans les bornes du split annoncé, et un split `holdout` est accompagné d'un `HoldoutAccessRecord` — que seul `load_holdout` produit, en exigeant une raison écrite et en incrémentant le compteur permanent. `describe_splits` compte les barres de chaque split **sans** consommer d'accès : montrer la taille du holdout dans l'UI ne doit rien coûter, compter n'est pas regarder. `load_holdout` journalise l'accès *avant* de lire les barres : un appel qui échoue ensuite a quand même consommé un accès, parce que le compteur mesure la décision de regarder, pas le succès de la lecture.

**Ce module refuse de faire.** Raccorder des futures sans méthode explicite, laisser un dataset en quarantaine atteindre le backtester, exposer le holdout sans raison écrite tracée, produire une sélection holdout par le chemin ordinaire (`load_split` lève), mélanger deux splits dans un même backtest, remettre un compteur d'accès à zéro, réécrire silencieusement un dataset déjà stocké (`dataset_id` dupliqué -> erreur), attribuer une conclusion positive à un warning (un dataset avec uniquement des `WARNING` reste `ok`).

**Limite connue (LSE).** Le module a été construit sans clé API : le contrat du vault (noms de colonnes renvoyées, format d'horodatage, comportement exact de la pagination côté serveur) est déduit de la lecture du SDK, pas vérifié en exécution réelle. Ce qui *est* vérifié : le protocole `LseClient` correspond exactement aux signatures de `lse.LSE` sous `mypy --strict`, et l'absence de clé produit une erreur nommant `LSE_API_KEY`. Le premier appel avec une vraie clé reste la vérification qui manque ; `normalise_candles` lève une erreur explicite nommant les colonnes reçues plutôt que d'inventer une barre si le schéma diffère.

**Statut.** Phase 0 (`HoldoutLockbox`, I3), Phase 1 (ingestion CSV/Parquet/Dukascopy/futures continus, contrôle d'intégrité, manifeste versionné, store DuckDB+Parquet) et le complément London Strategic Edge + sélection par split livrés.
